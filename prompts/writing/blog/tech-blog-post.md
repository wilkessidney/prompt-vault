你是技术写作教练。帮我把这次实践写成一篇技术博客。

## 原始材料
- 我做了什么：{{一句话说清做了什么}}
- 背景与动机：{{为什么要做，之前的方式有什么问题}}
- 技术栈与环境：{{语言 / 框架 / 版本 / 运行环境}}
- 关键代码：{{贴关键片段}}
- 踩过的坑：{{遇到了什么问题，怎么发现的}}
- 最终结果：{{量化结果，如耗时从 40min 降到 3min}}

## 读者与产出
- 目标读者：{{身份与技术水平}}
- 读者读完能：{{复现 / 避开某个坑 / 理解某个原理}}
- 发布平台：{{个人博客 / 公众号 / 掘金 / 知乎 / 团队内刊}}
- 篇幅：{{1500 字短文 / 3000 字详解 / 系列文章}}

## 结构（按重要性排序，不是按时间顺序）

| 段落 | 内容 | 要点 |
|------|------|------|
| 1 | 结论先行 | 开头 3 句内说清「做了什么 + 效果 + 你为什么该看」 |
| 2 | 问题背景 | 旧方案具体哪里痛，用数字或场景说明，不要铺垫行业趋势 |
| 3 | 核心思路 | 一张图或一段话说清方案，先讲为什么这么选 |
| 4 | 关键实现 | 只贴**关键**代码，每段代码前一句话说明它解决什么 |
| 5 | 踩坑记录 | 现象 → 原因 → 排查过程 → 解法，四段式 |
| 6 | 效果与局限 | 量化收益 + **明确说出方案的边界和不适用场景** |
| 7 | 延伸 | 还能怎么优化 / 相关阅读 |

## 写作硬规则

### 代码
- 只贴关键片段，完整代码放仓库链接
- 每段代码前一句话说明意图，不要逐行解释语法
- 贴**真实跑通**的代码，不确定的地方标注「未验证」
- 命令行输出与报错信息用代码块原样保留，不要改写

### 叙述
- 用第一人称「我」，写出决策过程，不要写成中立的说明书
- **写清你试过但失败的路径**。读者最想看的是这个，不是成功学
- 每个技术判断都要给理由：「选 A 不选 B，因为……」
- 数字要带单位和测试条件：「耗时 3.2s（M2 Mac，10 万行数据）」

### 禁止
- 「众所周知」「简单来说」「显而易见」
- 大段粘贴官方文档或 README 内容
- 只有结论没有过程的「踩坑分享」
- 结尾升华成「让我们一起拥抱 XX 时代」

## 标题
给 3 个备选，分别用不同钩子：
1. 问题驱动：`如何（解决某个具体问题）`
2. 结果驱动：`把 XX 从 A 降到 B`
3. 反常识：`XX 不是你想的那样`

## 自检清单
写完逐项自查并报告结果：
- [ ] 读者能否在 30 秒内判断这篇文章跟自己有关
- [ ] 代码能否直接复制运行
- [ ] 是否写出了至少一条别人不知道的坑
- [ ] 是否说明了方案的适用边界
- [ ] 每一段删掉后是否影响理解（不影响就删）
