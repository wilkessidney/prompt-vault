请直接为我开发并交付一套完整可运行、可打包、可分发的 Windows 桌面软件。不要只输出方案、界面示例、伪代码或零散片段；请创建完整项目文件、运行调试、修复错误，并在环境允许时打包出双击即可运行的 EXE。

软件定位：监控用户主动添加的小红书公开商品，定时记录商品累计已售、价格、店铺等公开信息，通过相邻快照计算商品和店铺的小时销量、今日销量、昨日销量与历史趋势。所有业务数据保存在本机 SQLite 数据库中。

执行要求：请严格按照下方规格一次性完成。

## 一、交付目标
交付内容至少包括：完整 Python 源码；SQLite 数据库初始化与自动迁移代码；Windows 桌面图形界面；定时采集与三级采集兜底逻辑；企业微信机器人通知；只读 MCP 数据服务；requirements.txt；README.md；一键打包脚本 build.bat；PyInstaller .spec 文件；最终无控制台黑框的单文件 EXE。代码必须是可维护的正式实现，不要把全部功能堆在一个巨大函数里，建议将界面、数据库、采集、统计、通知、MCP 拆分成独立模块。

## 二、技术栈
- Python 3.11 或 3.12。
- GUI：Tkinter + ttk，禁止依赖需要单独安装运行环境的前端框架。
- 数据库：SQLite，开启 WAL 模式，所有表都要自动创建，旧数据库缺少字段时自动迁移。
- HTTP：标准库 urllib.request，可使用系统 curl.exe 作为补充请求方式。
- 浏览器兜底：Playwright。优先系统 Chrome，其次 Microsoft Edge，最后 Playwright Chromium。
- 图片：Pillow，用于商品主图缩放与展示。
- 打包：PyInstaller，--onefile --windowed，运行时不得出现命令行黑框。
- 时间口径：全部使用 Asia/Shanghai。
- 软件首次运行自动在 EXE 同目录生成 monitor.db 和必要的数据目录。
- 所有外部进程在 Windows 下使用 CREATE_NO_WINDOW 或等价配置，避免采集时反复闪现黑色命令窗口。

## 三、商品输入和解析
添加商品必须同时支持：小红书分享口令（含标题、表情、短链和提取码的一整段文字）；xhslink.com 短链；完整商品链接（xiaohongshu.com/goods-detail/商品ID）；单独输入 24 位十六进制商品 ID。还必须支持批量导入：文本框一行一个，可混合放入口令、短链、完整链接和商品 ID。

解析规则：优先用正则从整段文字提取 /goods-detail/ 后的 24 位 ID，或直接提取独立的 24 位十六进制字符串；短链需跟随重定向，再从最终地址或返回页面提取商品 ID；商品 ID 统一转小写；批量导入按 ID 去重，已存在的商品跳过并计入重复；单个添加时先采集并展示商品名称、店铺、实际价格、累计已售，再弹窗让用户确认是否加入；批量添加结束显示成功、待采集、下架、重复、超过销量上限、无效输入各有多少个。

## 四、商品详情接口和字段解析
商品接口：
mall.xiaohongshu.com/api/store/jpd/edith/detail/h5/toc?version=0.0.5&item_id=商品ID

从 data.template_data[0] 中解析：商品标题优先 descriptionMain.name，回退 descriptionH5.name；店铺名称 sellerH5.name；店铺 ID sellerH5.id；商品主图 carouselH5.images[0].url，以 // 开头时补 https:；累计已售 priceH5.itemAnalysisDataText，支持「已售123」「1.2万」「1.2w」等格式；店铺累计销量 sellerH5.salesVolume；实际购买价格优先 priceH5.dealPrice.price，其次 bottomBarMainH5.dealPrice.price，再次 priceH5.highlightPrice，不能用优惠前原价覆盖实际到手价；粉丝数 profitBarPopupH5.follow.fansNum 或 sellerH5.fansAmount；库存状态 carouselH5.stockStatus；是否可配送 bottomBarMainH5.deliveryInfo.ableToDelivery。

只有当接口明确 success=true、template_data 完整存在时，空的已售字段才可解释为真实 0。请求超时、状态码异常、返回体不完整、页面未加载、JSON 解析失败、元素缺失或安全校验时，绝对不能用 0 代替，应判定本次采集失败，不保存假快照。累计已售按高水位处理：统计时取历史可信累计值的最大值，防止偶发读取变小造成虚假负销量；若新读数小于历史高水位，本轮不应用这个较小值计算销量。累计已售超过 10000 的商品不支持监控：添加时直接提示并跳过；存量商品一旦明确超过 10000，移出监控，停止继续请求。

## 五、三级采集策略
每个商品必须严格按以下顺序独立执行：1) 轻量接口直采；2) 当前商品直采失败后，立即使用静默浏览器采集；3) 静默浏览器仍失败时，立即使用可见浏览器兜底；4) 当前商品完成后，下一个商品重新从轻量接口直采开始。不允许先把全部商品走完第一种再统一走第二种。

静默浏览器要求：使用 Playwright 持久化 Context；headless=True，不显示窗口；locale=zh-CN，timezone_id=Asia/Shanghai；设置合理 viewport；整轮任务复用同一浏览器上下文；优先在浏览器中直接打开商品接口，接口无完整数据时再打开商品详情页，让页面建立正常会话后重新读取接口。

可见浏览器要求：只作为最后兜底；每次进入可见兜底前创建新临时 Profile；打开该商品详情页再读取商品接口；当前商品成功或明确失败后关闭窗口；默认逐个商品处理；临时 Profile 用完后安全清理。浏览器不可用时明确提示用户安装最新版 Chrome 或 Microsoft Edge，不能直接崩溃。请求之间默认随机等待 0.1～0.3 秒，允许在设置页改为 0.1～60 秒，使用随机区间而非固定值。

## 六、异常分类、重试和熔断
必须区分临时失败、风控、明确下架，不能混在一起。HTTP 500、连接超时、连接重置、DNS 临时错误、Network.getResponseBody、Execution context was destroyed 等属于临时错误，首轮先继续采集其他商品，整轮结束后等待 5～15 秒再统一重试一次。HTTP 461 属于请求环境受限，单轮连续出现少量 461 时记录，达到阈值后立即停止继续请求，把未完成商品加入队列，冷却 15 分钟后自动续采，禁止高频循环重试。自动重试成功后从失败列表移除并照常生成本地数据和企业微信时报。一个商品失败不能卡死整轮任务，除非触发全局 461 熔断，否则必须继续下一个商品。所有错误都要捕获并写入运行日志，界面线程不能因后台异常退出。

## 七、下架识别和下架列表
三种采集路径都必须识别下架：JSON 中购买按钮 type=unBuyableGoShop；页面或接口文字包含「已下架，进店逛逛」「当前商品已下架」「商品不存在」「商品已失效」；页面包含「当前商品违规，无法展示」、item freeze 等违规状态。不要仅凭网络错误、空白页面或超时判定下架，只有出现明确业务特征才能转入下架列表。

确认下架后：设置商品 active=0；记录 delisted_at 和 delisted_reason（区分商品已下架和违规下架）；清除普通失败状态；保留该商品原有历史销量快照；从竞品看板、店铺分析和以后所有采集任务中排除；继续采集下一个商品。下架列表位于失败列表旁，表格列为商品名称、店铺、商品 ID、下架时间、下架状态，双击可查看下架前的单品历史数据。

## 八、定时任务和整点规则
默认采集周期 60 分钟。用户在非整点点击开始监控后，不立即把该时刻当正式整点（例如 09:35 启动，第一次正式采集为 10:00，下一次 11:00）。支持修改周期，但必须按自然时间边界调度。每轮采集使用该轮整点作为统计归属时间。如果 21:00 轮次尚未完成，时间已到 22:00，必须停止 21:00 剩余任务，立即切换到 22:00 轮次，不得让旧任务无限积压。同时只能运行一轮采集，使用线程锁避免定时采集和立即采集重叠。GUI 必须保持响应，所有网络和数据库重任务放在后台线程，界面更新通过主线程调度。

## 九、SQLite 数据结构
至少建立以下表。products：id TEXT PRIMARY KEY、title TEXT NOT NULL、shop_name TEXT、shop_id TEXT、cover TEXT、active INTEGER DEFAULT 1、created_at TEXT、last_error TEXT、delisted_at TEXT、delisted_reason TEXT。snapshots：product_id TEXT、captured_at TEXT、sold INTEGER、shop_sold INTEGER、price REAL、fans INTEGER、stock_status INTEGER、deliverable INTEGER；复合主键 product_id + captured_at；为商品和时间建索引。settings：key TEXT PRIMARY KEY、value TEXT NOT NULL。logs：自增 ID、时间、级别、来源、商品 ID、商品标题、消息、完整错误详情，为时间建索引。deleted_products：记录用户主动删除的商品 ID 和删除时间，避免自动拓品时马上重新加入。数据库操作使用参数化 SQL，设置合理超时，开启 WAL。软件升级时通过 PRAGMA table_info 检测并补充新字段，不要求用户删除旧数据库。

## 十、销量统计口径
所有销量都由累计已售快照的差值计算，不能把累计已售直接当作当日销量。今日销量：当前可信累计已售减去今日 00:00 的累计高水位。昨日销量：今日 00:00 累计高水位减去昨日 00:00 累计高水位。上小时销量：当前整点累计高水位减去上一个完整整点小时的基线。某日销量：次日 00:00 累计高水位减去当日 00:00 累计高水位。当日每小时销量：相邻整点累计高水位差值。0 点快照既是前一天结束值，也是新一天基线，不能重复计入两天。若软件当天中途才开始监控，没有 00:00 快照，可使用当天第一条真实成功快照作为起始基线，界面允许显示为不完整口径。缺少足够基线时显示「—」，不要伪造 0。确认两个真实快照累计值相等时，销量增量才显示 0。模糊销售额：销量增量 × 当时实际价格，并明确标注「模糊试算，不代表真实成交额」。所有统计函数都应处理跨日、0 点、缺少快照、重复快照和累计值偶发回退。

## 十一、桌面界面总体风格
默认窗口 1280×780，最小 1050×650。字体优先 Microsoft YaHei UI。浅灰白背景，绿色作为主强调色，红色仅用于错误或风险。表格标题清晰、行高约 34、列宽合理，支持横纵滚动。不做花哨动画，优先信息密度和操作效率。紧邻标题区域显示：仅供学习交流，严禁用于商业用途，请于 24 小时内删除。右上角显示数据占用、运行状态和下次采集时间。右上角显示可点击的 by：冬青，点击打开 scys.com/personal/3941891?number=201255&tab=posts。

主界面使用横向 Tab，顺序固定为：竞品看板、添加商品、失败列表、下架列表、店铺分析、设置、运行日志。

## 十二、竞品看板
顶部左侧为竞品监控看板搜索框；右侧按钮从右向左：添加商品、自动拓品、智能去重、立即采集、开始 / 停止监控。表格列：商品名称、店铺、当前价格、今日销量、昨日销量、上小时销量、累计已售、最近采集、状态。搜索框实时匹配商品名称、店铺和商品 ID。今日 / 昨日 / 上小时 / 累计已售四列点击表头可排序，再次点击切换升降序，默认今日销量从高到低。双击商品打开单品数据弹窗。右键菜单支持查看详情、立即采集选中商品、删除商品。支持 Ctrl/Shift 多选并批量采集。删除必须二次确认，删除商品及历史数据后以后不再采集。待首次成功采集显示待采集；最近一次失败显示异常；成功显示正常。顶部不需要额外大型数据概览卡片。

## 十三、智能去重
只有同时满足以下条件才视为重复：同一店铺；商品标题标准化后完全相同；累计已售相同；上小时销量相同；商品 ID 不同；价格不同。每组只保留价格最高的商品，其他候选在删除前弹窗预览并二次确认。任一关键字段为「—」时不参与去重，避免误删。

## 十四、自动拓品和同店商品发现
当前限制（已无法使用，小红书不再支持未登录状态电脑版查看店铺商品）：添加主商品成功后，根据 shop_id 打开对应店铺主页，解析店铺内其他商品。店铺卡片中可能同时有 itemId 与 skuId，详情接口优先使用 skuId。自动拓品按钮执行：遍历当前监控商品对应的去重店铺；扫描店铺公开商品；排除已监控、已删除、已下架和本次重复的商品 ID；对新商品获取标题、店铺、销量、价格和封面；弹出选择窗口列出勾选框、标题、店铺、销量、价格、商品 ID；支持单选、全选、取消全选和批量加入监控。添加单个商品时，如果店铺还有其他未监控商品，提示店铺还发现了其他 X 个商品，展示名称和价格，由用户决定是否一起添加。店铺扫描失败只能记录该店铺失败，不能导致整个自动拓品任务退出。

## 十五、失败列表
失败列表只放临时采集失败和环境错误，不放明确下架商品。表格列：商品名称、店铺、商品 ID、最近失败时间、失败原因。按钮：全选、重试选中、忽略选中并保留监控、删除选中、刷新。所有操作支持单个和批量。重试成功后自动移出失败列表并恢复正常。重试后明确下架则移入下架列表。忽略只清除当前失败提示，商品下一轮继续采集。删除移除商品和历史数据，以后不再采集。双击失败商品也能查看已有历史数据。

## 十六、店铺分析和单品弹窗
店铺分析以店铺为核心。顶部提供店铺选择器，选择后显示店铺名称、监控商品数、累计已售、当前查看区间。时间选择：选具体日期显示该日期每小时店铺销量折线图和明细；快捷近 7 天显示七个自然日每日销量；快捷近 10 天显示十个自然日每日销量。下方左右分栏：左侧销量明细表（时间、销量增量、模糊销售额），右侧店铺内监控商品表（商品名称、今日销量、当前价格、累计已售、商品 ID），默认按今日销量从高到低排序，双击单品打开模态弹窗。单品弹窗展示：商品主图、商品名称、店铺、商品 ID、当前实际价格、累计已售、日期选择器、近 7 天和近 10 天快捷按钮、当天每小时销量折线图、多日每日销量折线图、销量明细和模糊销售额。图片加载失败时显示占位区域，不影响其他数据。

## 十七、企业微信机器人通知
设置页提供：Webhook 输入框、启用复选框、发送测试通知按钮、设置通知店铺按钮、当前状态文字。设置通知店铺点击后弹出店铺选择窗口，支持全选、取消全选、搜索和保存，只有勾选的店铺发送时报，未勾选不通知。每轮正式采集完成后发送店铺销量时报，按上小时销量从高到低排序。示例格式：

12点店铺销量时报
08月17日 12:00 - 12:59

金牌 XXXXXXXX的店
上小时销量：22 单
今日总销量：24 单

银牌 XXXXXXXX的店
上小时销量：16 单
今日总销量：20 单

前三名使用奖牌符号，其他使用序号。店铺名、上小时销量和今日销量清楚分行，消息过长时自动拆分，不能超过企业微信机器人单条限制。若有失败商品，再发送采集失败通知，含时间、采集方式、失败数量、商品名称、商品 ID 和原因。明确下架商品不作为临时失败反复通知。Webhook 必须校验格式，发送失败写入日志但不能影响采集数据保存。

## 十八、设置页
设置页按分组卡片纵向排列，内容较多时使用可滚动 Canvas。第一组监控设置：采集周期默认 60 分钟；商品间隔最小秒数默认 0.1；商品间隔最大秒数默认 0.3；保存设置按钮；打开浏览器处理验证按钮；当前商品数量和预估单轮等待时间。第二组企业微信机器人通知按上一节实现。第三组 AI / MCP 数据读取：显示一段可复制给 AI 的本地 MCP 配置说明；提供复制 MCP 配置说明按钮；清楚说明 MCP 只读，不允许修改数据库。

## 十九、只读 MCP 服务
提供独立 mcp_server.py，使用 stdio 通信，只读打开同目录 monitor.db，不得提供增删改工具。至少提供以下工具：list_shops（店铺列表、监控商品数、今日销量、上小时销量）；list_products（商品列表，可按店铺、关键词、状态筛选）；get_product_sales（指定商品某日小时销量或近 N 天每日销量）；get_shop_sales（指定店铺某日小时销量或近 N 天每日销量）；get_product_ranking（按今日、昨日、上小时、累计已售、模糊销售额排名）；get_shop_ranking（按店铺今日、昨日或上小时销量排名）；search_products（按标题、店铺和商品 ID 搜索）；get_overview（商品数、店铺数、今日销量、昨日销量、上小时销量、数据截止时间）。所有返回结果要包含口径和数据时间。MCP 查询与桌面界面使用同一套统计函数，避免两处结果不一致。设置页生成配置话术示例：

## 二十、运行日志
日志必须保存在 SQLite，重启不丢失。字段：时间、级别、来源、商品、商品 ID、摘要、完整详情。界面要求：按全部、成功、失败、信息筛选；刷新；清空日志二次确认；导出 CSV；双击查看完整异常详情并支持复制；商品采集失败时展示真实异常，不要只写失败；日志最多加载合理条数，避免界面卡顿。

## 二十一、本地数据占用和一键清理
右上角实时显示数据库占用大小和快照数量，例如：数据占用 19.1MB · 31,386 条。提供一键清理：默认保留最近 90 天销量快照；每个商品保留一条更早的基线，不能因清理导致近期销量无法计算；日志默认保留 30 天；执行 WAL checkpoint 和 VACUUM；清理前二次确认，清理后显示删除快照数、删除日志数、保留基线数和释放空间；清理逻辑始终可用，与其他功能开关无关。

## 二十二、稳定性和安全要求
不在源码中写死个人 Cookie；浏览器 Profile、Cookie 文件和数据库只保存在本机；日志不要输出 Cookie、Webhook 完整值或其他敏感字符串；所有后台线程异常都转成用户可读提示；关闭软件时尽量关闭 Playwright Context 和临时进程；数据库写入使用事务，防止中途退出留下半条记录；图片下载、商品请求、通知均设置超时；任何失败不能让整个 GUI 崩溃；对长标题、空店铺、无封面、零销量、价格缺失、跨日和夏令时无关的上海时区进行处理。
