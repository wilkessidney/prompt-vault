## 路线图结构
### 1. 债务优先级评分
每个债务给：
- 严重度：系统稳定性 / 性能 / 安全 / 可维护性
- 业务影响：影响多少用户 / 多少订单 / 多少收入
- 修复成本：人月估算
- 紧迫度：现在 / 季度内 / 年度内 / 可推迟

评分矩阵：
| 严重度  业务影响 | 高 | 中 | 低 |
|-----|-----|-----|-----|
| 高 | P0 立即 | P0 本季度 | P1 下季度 |
| 中 | P0 本季度 | P1 下季度 | P2 半年内 |
| 低 | P1 下季度 | P2 半年内 | P3 有空再说 |

### 2. 季度分配
- Q1：P0 债务清理 + 必要架构升级
- Q2：剩余 P0 + P1
- Q3-Q4：P2 + 主动预防性重构
- 原则：每季度 ≤20% 容量用于技术债

### 3. 债务清理策略
- 重构：完整重新设计
- 重写：局部重写
- 包装：抽象层包装
- 替换：用新组件替换
- 接受：明确接受债务 + 风险预案

### 4. 业务沟通
- 给业务的「为什么」：债务 X 影响 Y 用户 Z 收入
- 给业务的「何时」：Q 季度清理
- 给业务的「代价」：开发资源分配
- 给业务的「收益」：清理后能多支撑 N 倍流量

### 5. 度量
- 债务覆盖率：已识别债务 / 实际债务（建议定期扫描）
- 系统稳定性：故障率 / MTTR
- 开发效率：迭代周期 / Bug 率
- 性能：P95 延迟 / 吞吐

## 写作硬规则
- **每个债务给业务影响**：不只是「代码烂」，而是「影响 N 用户」
- 修复成本基于过往数据，不凭感觉
- 优先级评分有标准（避免拍脑袋）
- 不承诺「零技术债」（不现实）
- 业务沟通用业务语言，不用技术语言
- 度量指标可观测
