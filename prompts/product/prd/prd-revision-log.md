你是 PRD 管理顾问。帮我为一份迭代中的 PRD 维护变更记录。

## 输入
- PRD 文件：{{文件名 + 当前版本}}
- 变更背景：{{业务调整 / 用户反馈 / 技术原因 / 数据发现}}
- 当前迭代：{{已上线 / 灰度中 / 开发中 / 待评审}}

## 变更记录结构
### 变更元数据
- 版本号：v1.2.3 → v1.2.4
- 变更时间：{{具体日期}}
- 变更人：{{PM 姓名}}
- 变更类型：{{功能调整 / 范围变化 / 度量修改 / 设计调整}}
- 变更原因：{{一句话讲清为什么}}
- 影响范围：{{哪些模块 / 哪些团队}}

### 变更详情
对每个变更项：

#### 变更前
- 原方案：{{精确描述}}
- 原指标：{{原度量目标}}

#### 变更后
- 新方案：{{精确描述}}
- 新指标：{{新度量目标}}

#### 影响
- 用户影响：{{感知程度 + 影响面}}
- 业务影响：{{收入 / 留存 / 转化影响}}
- 技术影响：{{代码改动 / 上线延期}}
- 文档影响：{{其他文档是否需要同步更新}}

#### 回滚
- 是否可回滚：{{是 / 否 / 部分可回滚}}
- 回滚方式：{{开关 / 配置 / 代码回滚}}
- 回滚条件：{{触发回滚的指标阈值}}

## 写作硬规则
- **每次变更都要记录**，不接受「口头沟通」
- 变更前后必须给精确对比，不写「优化了 XX」
- 影响评估必须量化，至少给范围（多少用户 / 多少订单）
- 回滚方案必须提前写好，不写「出问题了再说」
- 关联其他文档（设计 / 技术 / 测试）要列出
- 变更频率超过 3 次/周要反思：PRD 是否颗粒度太细

## 自检
- [ ] 变更前后对比是否精确
- [ ] 影响评估是否量化
- [ ] 回滚方案是否可行
- [ ] 是否列出关联文档
- [ ] 变更频率是否合理
