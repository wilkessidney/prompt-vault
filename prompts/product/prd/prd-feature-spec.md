- 功能名：{{功能名 + 复杂度（高/中/低）}}
- 业务背景：{{为什么做}}
- 涉及方：{{后端 / 前端 / 设计 / 算法 / 运营 / 法务 / 财务}}
- 上线时间：{{deadline}}

## PRD 结构
### 1. 文档信息
- 版本、作者、评审人、最后更新

### 2. 背景与目标
- 问题描述：用数字 / 用户引用描述
- 业务目标：可量化
- 用户价值：可感知
- 成功标准：可验证

### 3. 需求详述
- 用户场景：3-5 个典型场景 + 角色 + 触发 + 期望
- 功能详述：每个子功能给：流程 + 边界 + 异常 + 权限
- 信息架构：菜单 / 页面 / 字段 / 关系
- 业务规则：3-10 条核心规则，每条给：触发条件 + 判断逻辑 + 后果
- 边界与不做：明确不做的边界

### 4. 设计与交互
- 关键页面：截图描述 + 交互说明
- 异常状态：每个异常给：触发场景 + 提示文案 + 系统行为
- 空状态：每个空状态给：触发场景 + 引导文案 + 系统行为

### 5. 数据与度量
- 埋点：每个关键动作给：事件名 + 属性 + 触发时机
- 主指标：1 个 + 计算公式
- 护栏指标：1-3 个
- 验证周期与决策规则

### 6. 依赖与风险
- 跨部门依赖：列出 + 时间节点
- 技术风险：列出 + 缓解方案
- 业务风险：列出 + 应急方案
- 上线计划：灰度策略 + 回滚方案

## 写作硬规则
- **每个边界都必须明确**，不接受「正常情况」「异常情况」
- 异常状态必须给完整处理：用户看到什么 + 系统做什么
- 业务规则用 if-then 句式，不写「正常情况下」
- 埋点必须在 PRD 阶段就定，避免上线后补
- 不写「等设计稿出了再补充」—— PRD 阶段就要写清楚
- 引用其他 PRD / 文档给具体链接

## 自检
- [ ] 边界与异常是否覆盖完整
- [ ] 业务规则是否用 if-then 句式
- [ ] 埋点是否在 PRD 阶段就定义
- [ ] 依赖与风险是否有缓解方案
- [ ] 总字数是否与复杂度匹配（建议 3000-8000 字）
